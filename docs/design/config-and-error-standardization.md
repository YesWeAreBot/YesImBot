# 配置组织与错误接口规范化设计草案

状态：首批核心配置导航及公共错误边界已实现；附加插件配置重排和其他错误抛出点的逐模块迁移仍属后续范围。重复标题局部修复已单独验证。

## 基线及限制

盘点基于 0038a9c，包含会话续接、群聊平衡算法及意愿连续性修复。模型提供商原生协议仍有独立的 #255 改动；实施模型配置整理前须结合其最终合入结果重新核对，不能覆盖或退回旧提供商配置。

本期设计不改变模型选择、回复策略、记忆作用域或默认启用状态。优先调整 Schema 的展示组合，不迁移配置字段。附加插件保留独立 Koishi 配置页和加载边界，通过一致的分类与文案形成统一体验，不要求所有插件配置复制进核心。

## 已核对的标题问题

`model/config.ts` 中 contextLimit 为带 description 的折叠 intersect。当前安装的 schemastery-vue 的 intersect 渲染器会在未设置 extra.foldable 时将父 meta 合并到内部块；内部 object 在 foldable=false 时将继承的 description 渲染成 h2。

局部修复在两个可见内部块上显式设置空 description，只阻止标题继承；外层说明、模式字段说明、数值/单位表格及隐藏校验继续存在。未修改 Vue 渲染器、配置路径、数据格式及容量解析。

### 分组实施前需定稿

1. 顶层导航名称、顺序、默认折叠以及高级选项边界。
2. 每项功能唯一主要入口；关联项使用简短说明，不复制可编辑字段。
3. 保留公开配置路径与默认值，移动前后使用同一组旧配置验证。
4. 能力声明、总开关、作用范围和执行策略分别命名，不将不同功能误删为重复。
5. 每个附加插件的分组采用共同词汇，但不由核心强制加载或修改插件配置。
6. 原生配置控件优先；隐藏或禁用无效组合前须确认配置保存与热更新行为。

## 错误体系现状

| 入口         | 现有结构                                                                           | 已确认的差异                                                                                       |
| ------------ | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 核心内部     | AppError / ErrorDefinitions，含 code、message、suggestion、errorId、context、cause | 已有基础类与稳定码，不应重建另一套                                                                 |
| 核心公开导出 | 根入口导出 shared，shared 导出 errors                                              | 错误类已有公开入口；问题是契约和使用覆盖，不是完全未导出                                           |
| 工具结果     | ToolCallResult / ToolError，错误含 name、message、可选 retryable                   | 未统一携带 code 与 errorId；Failed(string) 会丢失原始错误分类                                      |
| 工具异常捕获 | ToolService 捕获异常，日志后返回 Failed("Exception: ...")                          | 原始 code、cause 和关联关系不能可靠跨越边界；异常路径直接返回，结构化 retryable 路径才进入重试判断 |
| 人物插件     | 自建 Failed 包装为 PersonMemoryError，普通 Error 较多                              | 权限、参数、版本和来源失效通常只剩说明文字                                                         |
| OneBot 名单  | 本地 Failed 包装为 ToolError                                                       | 与核心 helper 形似，但不是统一转换入口                                                             |
| 视觉工具     | 混合 Failed(string)、普通 Error 及服务错误文本                                     | 需要按边界转换，不应将第三方响应正文直接当成稳定错误码                                             |

## 建议的最小公共约定

此处是设计候选，字段与命名须定稿后才进入实现。

- 内部沿用 AppError，保留 cause 与受控诊断上下文。
- 外部错误结果沿用 ToolCallResult，增量兼容 code / errorId 等字段；旧 name / message / retryable 保留读取兼容。
- 由统一转换入口从 unknown、AppError 或旧工具错误产生对应的公开结果。仅有相同 code 字符串不代表外部数据获得可信身份。
- 用户提示提供可行动说明和必要的错误 ID；模型工具结果提供执行结果及可恢复建议；维护日志保留 cause；上报使用现有白名单与系统配置。
- 不把无搜索结果或不存在可选记忆当成系统异常。

建议分类语义：输入无效、配置/能力缺失、权限拒绝、数据不存在、版本冲突、来源失效、取消、超时、限流、上游故障、内部故障、外部执行结果未知。先映射现有码，缺少的再按原有命名方式扩展；不批量重命名既有错误码。

重试资格由错误性质和具体操作共同决定。版本冲突通常需重读；权限、取消及确定失效不自动重试；发送或写入的结果未知不能因“网络错误”自动重做。声明 retryable 不代表绕过调用方的次数、幂等及取消限制。

## 接口边界验收候选

- 改变中文说明不会改变控制流。
- 普通无结果与执行失败可区分。
- 核心错误经过工具返回、日志和上报后仍能关联同一操作。
- 字符串错误与旧扩展返回可继续处理，未知错误不丢失内部 cause。
- 取消、版本冲突和权限拒绝不会被误判为可重试网络故障。
- 副作用回执未知时不自动重复执行。
- 对模型、用户及上报的结果不包含凭据、栈或未经批准的请求正文。
- 附加插件无需依赖核心私有文件；同进程重复包加载或跨进程传输不单靠 instanceof 判断格式。

## 配置导航具体方案（本批采用）

将当前按实现模块拆开的区域收敛为七个顶层分组。模型服务和回复触发默认展开，其余默认折叠；子功能保留独立折叠。此处“默认折叠”仅影响展示，不改变功能开关与配置默认值。

| 顺序与显示名称     | 子组                                                                                             | 现有根字段归属                                                                                                                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 模型服务         | 提供商与模型；模型组；任务分配                                                                   | providers、modelGroups、task                                                                                                                                                                                          |
| 2 人格与提示词     | 核心记忆文件；提示词模板；模板渲染（高级）                                                       | coreMemoryPath、systemTemplate、userTemplate、multiModalSystemTemplate、injectionPlaceholder、maxRenderDepth                                                                                                          |
| 3 回复触发与意愿   | 响应范围；直接触发；意愿算法；基础增益；回复成本与衰减；参与保持；话题；辅助判断；会话续接；暂停 | allowedChannels、prioritizeMentions、willingnessPolicy、base、attribute、interest、lifecycle、participation、topics、typesafe、continuation、replySuppression                                                         |
| 4 消息处理与工具   | 消息调度；工具调用方式；后台工具；扩展启用；工具重试与限制                                       | debounceMs、newMessageStrategy、deferredProcessingTime、heartbeat、nativeToolCalling、streamAction、backgroundTools、extra、advanced                                                                                  |
| 5 上下文与记忆     | 输入预算；图片上下文；近期消息；语义召回；长期日记；历史保留与清理                               | contextInputBudgetTokens、enableVision、allowedImageTypes、maxImagesInContext、imageLifecycleCount、detail、l1_memory、l2_memory、l3_memory、ignoreSelfMessage、logLengthLimit、dataRetentionDays、cleanupIntervalSec |
| 6 资源处理         | 保留现有资源服务字段，分存储与处理限制                                                           | storagePath、driver、assetEndpoint、maxFileSize、downloadTimeout、autoClear、image、recoveryEnabled                                                                                                                   |
| 7 日志、诊断与上报 | 本地日志；决策记录；错误上报                                                                     | logging、decisionRecording、errorReporting                                                                                                                                                                            |

version 继续隐藏，不作为导航字段。模型的生成参数、请求超时、重试、熔断、能力声明及容量仍留在各自模型内，不重复出现在工具执行限制中。资源处理的 image 子组保留缓存路径、尺寸、体积及 GIF 策略，autoClear 保留启用、周期和保留天数。实施前仍须对 Schema 做机械路径清单核对，并补入 #255 最终新增字段，不能把人工映射表当作完整覆盖验收。

### 各组展示约定

- 显示标题与配置路径分别维护。移动展示位置不把 `contextInputBudgetTokens` 写成新的 `context.budget` 路径。
- 保留 table、checkbox、computed 分支、动态模型/工具列表及高级参数的原生控件，不用文本框替换。
- 意愿的通用基础参数放在算法选择之后；平衡算法专用字段仍属于 willingnessPolicy，明确仅作用于平衡算法，不通过隐藏而丢失未启用算法的已保存参数。
- TypeSafe、话题分析和会话续接分别显示自己的启用条件及依赖；不增加一个会同时启用三者的总开关。
- 完成意愿仍放在后台工具内，因为它依赖任务完成处理与结算单位；响应意愿组只说明该奖励的存在，不再放第二套编辑入口。
- 图片上下文只负责模型本轮看到哪些图片；独立视觉工具负责图片查询与处理，其开关不假装是同一功能。
- 删除“高级选项”这类无对象的泛称，改为“工具执行限制”“模板渲染（高级）”等明确对象名称。
- 一个根字段只能在一处可编辑。跨组关联只用说明文字，不复制绑定同一字段的控件。
- 条件未满足时保留已填写值；第一批仅补充生效说明，不自动清空、覆盖或强行启用相关选项。

### 易混淆控制关系的明确表达

| 管理者的问题                 | 配置与解释                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| 模型最多容纳多少 token？     | 模型内 contextLimit；是容量声明，不是历史保留数量                                          |
| 每轮尽量给模型多少上下文？   | contextInputBudgetTokens；软预算为 0 不取消模型容量约束                                    |
| 保存多少近期聊天？           | l1_memory；与单次输入预算和数据库保留天数分开                                              |
| 是否使用原生工具调用？       | nativeToolCalling 为全局偏好；模型能力及 disableNativeToolCalling 可使该模型回退 JSON 动作 |
| 工具能不能进入后台？         | backgroundTools.enabled 与 allowedTools；不能据此推断普通工具被禁用                        |
| 回复过程中来了新消息怎么办？ | newMessageStrategy；与工具是否后台执行无从属关系                                           |
| 后台完成后是否主动处理？     | backgroundTools.completion；是否最终发言仍由意愿、调度及回复控制决定                       |
| 人物资料是否跨场景共享？     | 人物插件 sharedMemory / memoryDomain；与 recallScope 控制的经历召回范围区分                |
| 是否自动总结人物？           | 人物维护模式、总结模型组及任务条件共同决定；留空模型组不调用后台模型                       |

### 附加插件方案

人物记忆页保留“启用与维护模式 → 场景与共享范围 → 经历召回 → 后台总结 → 存储及维护限制”的顺序。已有字段保持原位置键，只重排展示。独立视觉、提醒、名单等插件统一采用“启用条件 → 功能参数 → 执行限制 → 存储/诊断（确有字段时）”；不存在的模块不添加空分组。

### 配置重排的验收门槛

1. 生成旧、新 Schema 根字段及完整路径清单：字段无丢失、无重复、无新增持久路径。
2. 同一批旧配置经过旧、新 Schema 后，业务值与默认值一致；computed 分支、动态选择、隐藏迁移和未知字段处理分别验证。
3. 在 Koishi 的真实配置渲染中检查折叠、保存、校验提示、未保存草稿、单行容量表和移动端窄屏；纯 schema 断言不替代视觉验收。
4. 启用、禁用、切换算法与切换模型能力后，已保存的不活跃选项不被清空。
5. 配置页实际载入的插件包与测试所用 schema 版本一致；先结合 #255 最终代码核对提供商相关控件。

## 公共错误接口具体方案（本批采用）

### 结构与兼容

沿用 AppError 作为内部错误类，ErrorDefinitions 作为错误码目录，ToolCallResult 作为工具结果，不新增第二个基础异常类。

拟议的增量公共 ToolError 结构：

```ts
interface ToolError {
    name: string; // 兼容现有工具
    message: string; // 面向调用者的说明
    retryable?: boolean; // 现有字段：表示资格，不承诺调用方一定重试
    code?: string; // 稳定错误码，新转换入口产生，旧工具允许缺少
    errorId?: string; // 同一错误跨日志、结果及上报的关联标识
    category?: ErrorCategory;
    suggestion?: string;
}
```

ErrorCategory 的候选固定值为 `invalid_input`、`configuration`、`permission_denied`、`not_found`、`conflict`、`source_invalid`、`cancelled`、`timeout`、`rate_limited`、`upstream_failure`、`internal`、`outcome_unknown`。category 是粗分类，code 是具体原因；不能通过 category 自动获得权限或触发重试。现有码保留，新目录条目再声明分类及可重试资格。

内部 AppError 保留 cause/context；这两个字段不加入公开 ToolError。ErrorDefinitions 中已有 code/message/suggestion 的条目继续可用，新增元信息应可选。普通 Error 规范化后以其为 cause，不直接将任意异常正文作为公开说明。

### 边界职责

| 边界                   | 必须保留                                        | 不应直接传出                       |
| ---------------------- | ----------------------------------------------- | ---------------------------------- |
| 内部服务到内部调用方   | AppError 的具体码、关联 ID、cause、受控上下文   | 不以中文文案做分支依据             |
| 内部错误到模型工具结果 | code、分类、可行动说明、重试资格和必要的关联 ID | 栈、凭据、原始请求及响应正文       |
| 管理指令到用户         | 简明原因、下一步操作、必要的错误 ID             | 内部对象与完整调用栈               |
| 维护日志               | 同一 errorId、操作/工具标识、经处理的诊断详情   | 未处理的敏感请求内容               |
| 外部错误上报           | 沿用已配置的上报开关、过滤与字段白名单          | 不能因为错误被规范化就默认开启上报 |

### 处理语义

- 成功但无查询结果：仍是成功结果，不能转换为内部异常；必需对象不存在才属于 not_found。
- 来源删除、身份归属变化与暂时读取失败分开，暂时失败不能直接将数据判为永久失效。
- 版本冲突先重新读取并重新决定操作，不能盲目重复旧提交。
- 取消、权限拒绝、参数错误和明确来源失效不自动重试。
- 超时、限流和上游故障仍受具体工具的幂等与次数约束；已执行但回执未知归 outcome_unknown，不自动重做副作用。
- 对插件显式返回的旧 ToolError 保持 name/message/retryable 行为；逐步补齐新字段，而不是猜测中文文本对应的错误码。
- 对来自普通对象的错误先验证字段类型与长度；不能只凭 `instanceof` 跨包判断，也不能仅凭外部 `code` 字符串将其当作可信 AppError。
- 边界只进行一次有明确归属的规范化和记录，避免每层重新生成 errorId 或重复上报。

### 分阶段贯通与验收

首条贯通链建议选择人物记忆的“读取当前人物 → 提交带版本的候选 → 版本冲突返回”：既有真实普通 Error 和自建 Failed 包装，也已有版本保护，可验证分类而不改变人物认识算法。

第一步定稿错误类别、字段与转换入口签名；第二步补兼容测试及该条链路；第三步接入 ToolService 捕获与返回；第四步按插件扩展。取消/重试与副作用未知的用例应在工具服务接入时一并验证，不能仅在人物读取场景测试后宣称全链完成。

第一批不批量替换所有 throw，不修改既有工具成功结果，不增加自动重试次数，不将模型错误与工具错误的重试策略合并。配置展示与错误规范应分开提交与验收。

## 首批实施结果与验证边界

- 核心配置已按七组重排，原根字段仅出现一次，复用原生字段 schema；子分组使用独立 `yib-subsection` 角色与三级标题，折叠不卸载内部表单。
- 原有配置、默认值、computed 分支、动态选择及上下文容量转换均与重排前组合对照验证。
- AppError 增加分类及重试资格，旧构造方式继续可用；ToolError 增量增加可选 code/errorId/category/suggestion。共享 normalizeAppError、fromAppError、toToolError 提供内部规范化和公开白名单投影。
- ToolService 异常捕获采用共享转换，保留取消检查与原重试次数；显式旧 ToolError 返回及 Failed(string) 继续兼容。
- 人物候选与 claim 候选的版本冲突已贯通 `PERSON_MEMORY.VERSION_CONFLICT`；旧核心缺少该目录时回退原错误说明，版本保护仍执行。
- 本地自定义 AppError 保留对象、cause 与关联 ID；未注册码对外回退安全的未知错误说明；跨包对象须通过受限结构检查。
- 附加插件其他普通 Error 及独立配置页尚未全量改造，不应据此宣称所有插件已经统一错误分类。
- 配置组件已验证服务端渲染的标题、展开状态、内部挂载与字段前缀传递；完整 Koishi 浏览器交互及真实主题下的窄屏视觉仍需部署验收，不能用 schema 或服务端渲染测试替代。
