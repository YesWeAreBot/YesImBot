# YesImBot 人物记忆

独立可选插件：`koishi-plugin-yesimbot-extension-person-memory`。

按账号认人、为人物保存画像，同时允许管理员查看来源、修改关联、审核模型候选、锁定画像和回滚修改。使用 Koishi 已配置的数据库，SQLite 即可；不要求 embedding、RAG 或 Jev。YIB 原有 L1/L2/L3 继续工作，人物资料通过现有动态提示词注入。

## 共同记忆试开发

共同记忆需要同时使用本试开发版本的核心和人物插件；已有 3.0.4 核心如果缺少 `memoryCorrectionFilter: 1`，会在注册前拒绝共同模式，避免只更新插件后旧摘要仍误导 Bot。

开启 `sharedMemory` 后，同一 Bot 的群聊和私聊共用人物认识与持久经历。人物以平台和账号 ID 识别，昵称变化不会拆成新人，同名也不会自动合并。跨平台账号需要明确关联；可让模型提出，也可让管理员绑定。

```yaml
enabled: true
sharedMemory: true
memoryDomain: "shared-bot" # 需要显式共享记忆的 Bot 账号填相同值；留空按平台和 Bot 账号区分
mode: review
recallScope: mind # mind：域内当前配置允许的会话；current：仅当前会话召回
automaticRecall: true
memoryRetentionDays: 0 # 原始经历召回表不按时间清理；不改变画像来源和审计的保留规则
modelGroup: "" # 留空不调用后台总结模型，主模型仍可使用工具
```

默认 `sharedMemory: false` 保留原场景档案。切换不会自动合并或重写旧数据；在各个旧场景执行 `people.import`，只导入共同域中尚不存在的账号，保留旧账号分组、可用画像和锁定状态，已有共同画像不覆盖。旧来源保留原平台、Bot、频道、消息 ID 和时间。导入不会整批读取核心历史，也不会触发额外模型调用。

| 模式     | 行为                                                                     |
| -------- | ------------------------------------------------------------------------ |
| `off`    | 停止新记忆采集、人物注入、召回和模型读写；原有 Bot 聊天继续，旧数据保留  |
| `review` | 读取记忆、提出画像或关联候选；管理员批准后生效                           |
| `auto`   | 新鲜、有实际来源且版本正确的画像和账号关联可自动接受；管理员仍可随时干预 |

控制台 `mode: off` 在注册新记忆功能前退出。命令 `people.mode off` 关闭当前共同域的新记忆功能，管理员命令仍保留以便恢复。`people.pause` 只暂停模型维护，读取、采集和人工编辑继续。切换模式不自动批准既有候选。锁定、暂停、来源与版本检查在 `auto` 中同样生效。

共同域中沿用下文管理命令，另有 `people.recall <关键词>` 和 `people.import`。账号参数默认指当前平台；跨平台可用 JSON 形式 `["平台","账号ID"]`（命令中需要适当引号），人物 UUID 可用于查看与人工管理。模型提交候选必须指定账号，不能用人物 UUID 代替。所有管理命令要求 authority ≥ 3。

`person_recall` 允许主模型按关键词、人物、起止日期主动查询旧经历和核心 L2/L3 摘要；用户明确提及“记得、之前、上次”等时，也会尝试一次自动查询。结果包含来源定位和时间，实际发言仍是未经核实的陈述。查询遵守当前插件筛选和 YIB 允许频道配置，不会把空目标范围扩大为全库。

身份绑定、拆分、合并或撤销后，旧归属版本的经历暂时退出自动召回；原始记录不会改写。人工修改画像后，相关旧摘要也会暂时退出召回。没有人物元数据的旧摘要在无法安全区分时保守过滤。此过滤同时作用于 `person_recall` 和核心原有 L2/L3 自动注入，重新读取最新版本不能绕过旧来源失效检查。管理员仍可查来源与审计，并根据纠错后的新发言重新建立认识。

框架维护事件会进入模型上下文，包含发起者、操作、时间、平台/适配器、目标、作用范围和结果。共同域维护在域内可见；工具服务的全局变更在各个会话可见。命令“已调用”“观察到返回文本”和工具“成功/失败回执”分别记录，返回文本不被当作业务成功证明。回复暂停记录实际管理员与目标；历史清理失败明确提示可能已经发生部分删除。事件投递失败不会撤销已经接受的记忆修改。

试开发边界：召回使用关键词和日期，尚未接入跨域向量检索；每次最多检查 200 条匹配经历、20 个频道、每频道每类 50 条核心摘要，最多返回 12 条。明确日期可用于缩小候选范围。新来源从启用之后积累；后台总结仍只使用近期来源，域内共享原有 2000 个档案和 50 个待审候选上限。`memoryRetentionDays` 仅影响经历召回表，画像来源和完整审计另行保留。核心 `history.clear` 不删除本插件资料。共同域注入最多约 12000 字符，工具回忆最多 10 秒，超时跳过本次自动回忆。

以下介绍原场景模式；其中“账号关联始终人工审核”和“不能跨群”仅适用于 `sharedMemory: false`。

## 启用

安装插件，启用数据库和 YesImBot，在 Koishi 控制台添加 `yesimbot-extension-person-memory`。需要 YesImBot ≥ 3.0.4，或同时公开 `beforeUserStimulus v1` 与 `trustedToolSession v1` 能力的源码构建，确保本轮推理前已经完成账号识别和消息来源记录。旧发布核心 3.0.3 不支持这两项能力，插件会在注册模型、工具、命令、监听及后台任务前明确拒绝启用，请先升级核心；不会回退到不可信的模型工具会话。插件所用 Koishi 服务为 `database` 与 `yesimbot`：核心子服务通过 `ctx.yesimbot.prompt`、`ctx.yesimbot.tool`、`ctx.yesimbot.world` 访问，后台总结还会使用 `ctx.yesimbot.model`。

先使用默认 `review` 模式。后台总结模型组留空时，不额外调用模型；人工编辑和主模型提交候选仍可用。

```yaml
enabled: true
mode: review
modelGroup: "" # 改成已有 YIB 模型组名称后才启用后台总结
summaryThreshold: 6
cooldownSeconds: 600
timeoutSeconds: 30
maxQueue: 32
```

只处理 YIB 允许的频道中的普通用户消息，跳过机器人和管理命令。新账号得到独立 UUID 临时档案，同名账号不会自动合并，改昵称也不改变 UUID。首次安装只从之后见到的消息开始积累来源，不导入全群历史。

后台总结的模型组列表由核心提供。先启动核心，再从列表选择已有模型组；修改核心模型组后需启动或重载核心以更新列表。原有文本形式的组名仍可读取；留空保持不调用后台模型。共同记忆域、回忆范围和排查示例见[命令与意愿评估排查](../../docs/command-troubleshooting.md)。

## 结构化画像与结尾概述

新画像包含背景身份、目标动机、行为场景、痛点需求、交流偏好、重视的原则，以及各场景的近期记录、禁忌与可切入话题。未知内容保留空数组，不要求模型填满。最后的概述从这些字段生成；字段变更、审核、撤销与回退同时处理结构化内容和概述，避免两份资料相互矛盾。

旧版纯文本画像继续可读，不会被自动猜测为结构化事实。配置后台总结模型后，可执行 `people.summarize <账号ID>` 生成重新整理候选；`review` 模式仍需审核，人工锁定仍生效。主模型也可使用 `person_memory` 提交完整结构化候选，无需启用额外后台模型。

控制台的“人物画像写作规则”（`profileSystemPrompt`）可编辑。已有画像和来源以独立数据提供，固定的字段格式、来源与版本检查继续生效。每次更新整合完整认识，允许修正和删除重复内容，不将聊天原句无限追加。

活跃度由程序按消息时间计算，窗口为连续 168 小时，活跃天数按 UTC 日期去重，最多可能跨 8 个日期。统计仅覆盖插件实际捕获且身份归属仍有效的记录，不代表完整群历史。话题、情绪、事件和互动是模型对最多 40 条近期样本的归纳；最多列出 5 个话题，不提供未经全量分类验证的精确频率排名。场景记录标明统计起止时间；过期快照不应作为当下情绪和活动的依据。

长期认识随已确认的人物关联共享；群昵称、近期记录和交流边界按场景保存。共同模式读取场景栏目时同时遵守 `recallScope`、插件筛选和允许频道配置。曾发生分歧不等于永久“冲突对象”，一次玩笑也不直接成为长期偏好或禁忌。

### Bot 列表与批量读取

`person_memory` 增加以下只读操作，Bot 可以先列出人物，再用明确 ID 选择目标：

```json
{"action":"list"}
{"action":"read_many","account_ids":["账号ID或人物UUID","另一个ID"],"fields":"full"}
{"action":"read_many","all":true,"fields":"structured"}
{"action":"read_many","cursor":"上一页返回的nextCursor"}
```

`account_ids` 与 `all` 互斥；关联到同一人物的多个账号只返回一份档案。`fields` 可选 `overview`（默认概述）、`structured`（结构化栏目）和 `full`（完整资料）。原有 `read(account_id)` 仍可读取单个人物。

结果提供 `total`、`returned`、`hasMore` 和 `nextCursor`。每页最多 20 人，并按实际响应字节数分页；不会把半份档案当作完整结果。查询快照有效期为 5 分钟，继续时可只提交相同操作与游标。人物版本、关联或权限变化后需重新查询，不能继续使用旧快照。分页读取不调用总结模型，也不修改画像。

管理员用 `people.edit_json <ref> <完整JSON>` 提交完整结构化资料，结尾概述自动同步；`people.edit` 继续用于完整替换为旧版纯文本格式，替换前的版本可查审计与回退。

## 管理员命令

以下命令需要 Koishi authority ≥ 3。场景模式只操作当前群频道或私聊；共同记忆模式操作当前共同域，可能影响其他关联场景。`ref` 可用账号 ID 或人物 UUID，不能用昵称代替。用 `help people` 查看命令。

| 命令                                                     | 用途                                                                                               |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `people.status`                                          | 模式、暂停状态、数量、模型配置、运行账号、队列、最近总结结果或错误                                 |
| `people.list [offset]`                                   | 分页列出人物，每页 20 个                                                                           |
| `people.create <称呼>`                                   | 创建独立人物，返回 UUID                                                                            |
| `people.show <ref>`                                      | 完整画像、账号关联、确信度、版本、锁定、需复核及身份关联曾改变的提示                               |
| `people.rename <ref> <称呼>`                             | 修改心中称呼；中文直接使用，不改平台昵称                                                           |
| `people.sources <账号ID>`                                | 最近 10 条消息证据，含原始账号、昵称、消息 ID 和时间                                               |
| `people.bind <账号ID> <人物UUID或账号ID> [确信度]`       | 人工修正关联；确信度默认 1，范围 0–1                                                               |
| `people.unbind <账号ID>`                                 | 解除旧关联，为该账号建立新的独立临时档案                                                           |
| `people.merge <来源ref> <目标ref>`                       | 合并人物，来源人物的账号转到目标人物，画像标为需复核                                               |
| `people.split <账号ID> <新称呼>`                         | 把一个账号拆到独立新人物，旧画像标为需复核                                                         |
| `people.edit <ref> <完整画像>`                           | 人工替换画像，并清除需复核标记；旧内容留在审计历史                                                 |
| `people.clear <ref>`                                     | 清空当前画像，保留历史和来源                                                                       |
| `people.archive <ref> [画像版本]`                        | 不带版本先预览人物及关联账号；确认版本后归档，释放档案容量，保留历史和来源                         |
| `people.lock <ref>` / `people.unlock <ref>`              | 禁止/允许模型更新该画像；管理员仍可编辑，合并前需解锁                                              |
| `people.summarize <账号ID>`                              | 手动触发总结，仍遵守锁定、审核模式和来源限制                                                       |
| `people.pending [候选UUID]`                              | 列出画像及账号关联候选；指定 UUID 查看完整候选和证据                                               |
| `people.approve <候选UUID>` / `people.reject <候选UUID>` | 接受或拒绝；身份或版本已经改变时不能直接接受                                                       |
| `people.history [修改UUID]`                              | 每页 10 次修改，支持 `--page`、`--account`、`--person`、`--action`；指定 UUID 查看完整前后差异     |
| `people.revert <修改UUID>`                               | 条件回滚；相关对象有后续变更时拒绝覆盖，需人工修正                                                 |
| `people.pause` / `people.resume`                         | 暂停/恢复当前场景的模型维护，暂停仍可查询和人工编辑                                                |
| `people.mode <off\|review\|auto>`                        | 当前场景关闭新记忆功能、人工审核或自动接受画像；账号关联候选始终需人工审核，切换不自动审批已有候选 |

确信度是管理员表达的身份信念，不是统计校准概率，也不能用作管理员权限、账号所有权或授权证明。`pause` 不停止账号识别、来源记录及既有画像读取；`off` 停止新采集、注入和模型读写，管理员仍可恢复模式。控制台设为 `off` 或禁用插件会在注册前退出。

### 从群友名单到人工确认

如已安装 OneBot 名单插件，可先在当前群查询账号，再建立关联：

```text
onebot.contacts.members -n 20
people.create 许仙
people.bind 123456789 <上一步返回的人物UUID> 0.9
people.show 123456789
people.sources 123456789
people.summarize 123456789
people.pending
people.pending <候选UUID>
people.approve <候选UUID>
people.lock 123456789
```

名单插件提供平台联系人事实，人物记忆插件维护“认作谁”和“记得什么”。名单账号可以先人工绑定；有普通发言后才积累总结证据。好友名单仍使用 `onebot.contacts.friends` 的既有权限规则，本插件不会把名单整批发给模型或自动建画像。

### 认错之后

```text
people.pause
people.show <旧账号ID>
people.history --account <认错的账号ID> --page 1
people.split <认错的账号ID> 新称呼
people.sources <认错的账号ID>
people.edit <旧人物UUID> 核实后保留下来的完整画像
people.resume
```

原始消息和证据中的账号不会被改成人物昵称。旧画像被标为需复核后，默认模型上下文和模型读取会暂时隐藏其正文；管理员仍能查看旧内容。画像复核或重新总结可以恢复正文，但“身份关联曾改变”提示会保留，提醒模型核对可能混同的旧 L2/L3 记忆。重新总结只采用当前关联账号的证据，不自动改写核心 L2/L3 历史或删除当时产生的记忆。

翻查较早的记录可用 `people.history --account <账号ID> --page 2`；`--person <人物UUID>` 按人物查，`--action bind` 等筛选操作类型。账号筛选会追溯其旧关联人物；`--account` 和 `--person` 二选一。

不再活跃的档案可以先执行 `people.archive <人物UUID>` 预览，再用 `people.archive <人物UUID> <预览中的画像版本>` 确认。归档移除当前人物、关联账号及相关候选；来源和审计保留，条件允许时可通过 `people.revert` 恢复。该账号之后再次发言会建立新的临时档案，继续保留身份关联改变的提示。

## 模型如何使用

当前说话者和 L1 最近活跃账号最多 6 人自动进入上下文，总计不超过 6000 字符。每个人最多注入 600 字画像；完整资料可通过 `person_memory` 查询。包含临时档案标记、UUID、账号关联确信度、锁定、需复核、身份关联曾改变的提示及待审核候选。平台消息 sender 保持原样。

上下文优先保留人物和账号的关联字段，画像按剩余空间缩短；可用 `person_memory read` 查询完整画像。

`person_memory` 提供列表、批量读取、画像与逐条认识操作：

- `read`：传入 `account_id`，读取当前场景画像、账号关联和版本。
- `search`：传入 `query`，按称呼/画像关键词返回最多 5 个简短结果，不依赖向量检索。
- `history`：传入 `account_id`（账号 ID 或人物 UUID），读取最近 10 次相关修改的元数据及有限变更摘要，不返回原始证据正文；完整差异由管理员用 `people.history` 查看。
- `propose`：传入 `account_id`、完整 `profile`、1–10 个 `message_ids`，以及从上下文或 `read` 取得的 `person_id`、`person_revision`、`account_revision`。来源必须是本插件实际记录的当前场景、当前账号消息；过期版本拒绝写入。
- `propose_link`：提交账号关联建议，包含上述来源及版本字段，以及目标人物 `target_person_id`、`target_revision`、`confidence` 和不超过 500 字的 `reason`。目标人物必须属于当前场景，候选始终等待管理员确认。

模型不能直接改账号关联、合并、拆分、审批、锁定或跨场景读取。画像默认提交待审核候选；`auto` 模式满足来源、版本和锁定检查后接受画像，账号关联候选仍需人工审核。来源检查证明消息来自哪里，不证明摘要理解正确，管理员可随时干预。

后台按账号累计消息、批次总结，全局最多一个模型请求，同一账号有冷却期，默认最多 32 个待处理任务。失败不会中断回复；`people.status` 可查看当前进程内最近结果/错误。任务输入、模型输出、处理进度与重试时间保存到数据库，重载后继续处理；已接受结果使用持久回执避免重复提交。恢复、调用模型及接受结果时会重新检查来源频道权限；来源归属不明或权限已撤销的任务停止处理。关闭、暂停、锁定和版本变化仍会阻止写入；卸载保留未完成任务，管理员取消会使旧任务失效。队列协调适用于同一进程内的插件实例，不提供跨进程工作器锁。

## 逐条认识与来源

使用 `claims` 分页查看人物的逐条认识；`claim_evidence` 按 `claim_id` 分页读取对应原始证据。返回的旧证据属于回读，不会因为再次读取、转述或摘要而变成独立新证据。每条来源的 `uses` 标明它用于哪次补证、反证或修订及当时陈述，避免把反例误当支持。

`propose_claim` 提交 `changes`，支持 `support`（补充来源）、`counter`（反例）、`revise`（修订）和 `retire`（停用）。已有认识必须携带 `claimId` 与 `expectedRevision`，同时提供最新人物、账号版本。分类和场景不能在修订时偷换；补证、反证和停用不能改写陈述，改写须使用 `revise`。重复提交同一原始证据返回 `unchanged`，不新增候选、审计或人物版本；支持、反例和修订需要 1–10 个当前允许的原始来源 ID。反例会使认识进入争议状态并从当前画像中移除，明确修订后才恢复。已停用认识必须以新的独立来源明确修订，旧来源无法自动恢复它。

逐条认识会同步生成结构化字段与结尾概述，仍遵循审核、锁定、暂停、来源权限及回退规则。首次从完整画像转入逐条维护时，旧正文保留在 `legacyProfile`，旧结构保留在 `legacyStructuredProfile`，不自动当作新认识的证据。当前栏目与结尾概述只从有效认识重建，不再混入没有逐条来源的旧结论；查询返回的旧正文明确标记为 `unmanaged_snapshot`，且遵循场景权限。身份关联改变后，旧资料单独标记需复核，新来源支持的有效认识仍可使用。已有逐条记录后，模型使用逐条变更维护；管理员明确重置正文会停用旧记录。身份关联变动后，旧画像仍须复核，不会因为接受一条新认识而自动恢复全部旧内容。

配置后台模型时，已有逐条记录的人物使用同一套变更规则；尚无逐条记录的旧画像保留原有重新整理路径。没有配置后台模型，不会新增后台模型调用。

## 数据与边界

- 按平台、机器人账号、群频道或私聊对象隔离。同一账号在另一个群有独立档案；第一版没有跨群识别或跨群记忆入口。
- 画像来源保留最近七天已捕获记录，并至少保留原有最近 200 条快照，每条最多 1000 字符；候选引用的快照独立保存，不因近期缓存淘汰而丢失。旧版纯文本候选最多 2000 字，结构化档案有独立字段和总大小限制；每个画像最多携带 20 条来源，更早的修改和来源可查审计记录。
- 每场景最多 50 个待审核候选（画像和账号关联合计）、2000 个账号及人物。达到档案上限可用 `people.archive` 归档不再活跃的人物，释放容量。人物/关联/候选是带 revision 的场景 JSON 状态，审计差异和近期来源分表持久化；这版适合群聊规模，暂不提供大型全局人物库。
- 待审上限只限制新增待审核候选；`auto` 直接接受的画像不占用待审容量，仍须通过来源、版本、暂停和锁定检查，检查失败时不会写入。
- 人物更新与审计以同一条带 `format=1` 的审计 INSERT 原子提交，以场景和下一 revision 的唯一 ID 仲裁并发；冲突重新读取并校验，持续竞争时最多重试 16 次后报错，不会静默覆盖。条件回滚后的版本继续递增，阻止旧模型结果趁回滚重新生效。人物写入不使用共享数据库事务，失败或取消不会回滚其他频道和插件已经接受的普通写入。YIB 自己的后台保留期清理也以独立删除重试，避免清理失败撤销并发接受的记录；SQLite 共享连接仍有驱动边界，第三方插件自行打开事务时，其回滚可能影响同连接上的普通写入，本插件不能隔离第三方事务。
- 状态表是可重建缓存，缓存写入失败或倒退不会否定已接受的提交；读取会按 revision 重放后续提交并尝试修复缓存。新场景首条提交保留模式默认值；旧库首次新格式提交在同一条记录保存旧 revision 和完整状态基线，不改变原审计差异与撤销含义。旧 UUID 审计继续可查和条件回滚。升级前请保留完整备份，并停止旧版本人物插件写入；新格式启用后不能直接降级为只读状态表的旧实现，也不能单独删除/截断审计表。基线建立前仍需旧状态表，建立后缓存丢失可由完整提交日志恢复。
- 取消在最终 INSERT 派发前生效；已派发的写入等待数据库完成，成功即视为接受，卸载与迟到取消不会再回滚已提交内容。来源以场景和消息 ID 唯一 INSERT，重复消息不改写原证据；接受后的来源淘汰失败只会暂时多保留快照，下次采集再清理。
- 人工完整编辑没有新消息来源，审计明确记录管理员及旧证据。`clear` 是清空当前画像，不是删除历史；如有完整数据删除要求，需要同时处理本插件的状态、来源、审计、总结队列、已启用的共同记忆经历表及核心历史。
- 卸载停止后台任务并移除工具/注入，数据库内容保留。候选/画像内容会发往管理员配置的模型服务；开启后台模型组或 `auto` 前，应了解本群的记忆使用约定。

本插件不把身份确信度接到 Jev 回复概率或管理权限上。之后可按需要增加候选排序、其他检索后端或人工确认入口。
