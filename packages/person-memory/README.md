# YesImBot 人物记忆

独立可选插件：`koishi-plugin-yesimbot-extension-person-memory`。

按账号认人、为人物保存画像，同时允许管理员查看来源、修改关联、审核模型候选、锁定画像和回滚修改。使用 Koishi 已配置的数据库，SQLite 即可；不要求 embedding、RAG 或 Jev。YIB 原有 L1/L2/L3 继续工作，人物资料通过现有动态提示词注入。

## 启用

安装插件，启用数据库和 YesImBot，在 Koishi 控制台添加 `yesimbot-extension-person-memory`。需要 YesImBot ≥ 3.0.4，或同时提供 `beforeUserStimulus: 1` 与 `trustedToolSession: 1` 核心服务能力的源码构建，确保本轮推理前已经完成账号识别和消息来源记录。旧发布核心 3.0.3 不支持这两项能力，插件会在注册模型、工具、命令、监听及后台任务前明确拒绝启用，请先升级核心；不会回退到不可信的模型工具会话。插件所用服务为 `database`、`yesimbot.prompt`、`yesimbot.tool`、`yesimbot.world-state`，后台总结还会使用 `yesimbot.model`。

先使用默认 `review` 模式。后台总结模型组留空时，不额外调用模型；人工编辑和主模型提交候选仍可用。

```yaml
enabled: true
mode: review
modelGroup: ""         # 改成已有 YIB 模型组名称后才启用后台总结
summaryThreshold: 6
cooldownSeconds: 600
timeoutSeconds: 30
maxQueue: 32
```

只处理 YIB 允许的频道中的普通用户消息，跳过机器人和管理命令。新账号得到独立 UUID 临时档案，同名账号不会自动合并，改昵称也不改变 UUID。首次安装只从之后见到的消息开始积累来源，不导入全群历史。

## 管理员命令

以下命令需要 Koishi authority ≥ 3，且只操作发出命令的当前群频道或私聊。`ref` 可用账号 ID 或人物 UUID，不能用昵称代替。用 `help people` 查看命令。

| 命令 | 用途 |
| --- | --- |
| `people.status` | 模式、暂停状态、数量、模型配置、运行账号、队列、最近总结结果或错误 |
| `people.list [offset]` | 分页列出人物，每页 20 个 |
| `people.create <称呼>` | 创建独立人物，返回 UUID |
| `people.show <ref>` | 完整画像、账号关联、确信度、版本、锁定、需复核及身份关联曾改变的提示 |
| `people.rename <ref> <称呼>` | 修改心中称呼；中文直接使用，不改平台昵称 |
| `people.sources <账号ID>` | 最近 10 条消息证据，含原始账号、昵称、消息 ID 和时间 |
| `people.bind <账号ID> <人物UUID或账号ID> [确信度]` | 人工修正关联；确信度默认 1，范围 0–1 |
| `people.unbind <账号ID>` | 解除旧关联，为该账号建立新的独立临时档案 |
| `people.merge <来源ref> <目标ref>` | 合并人物，来源人物的账号转到目标人物，画像标为需复核 |
| `people.split <账号ID> <新称呼>` | 把一个账号拆到独立新人物，旧画像标为需复核 |
| `people.edit <ref> <完整画像>` | 人工替换画像，并清除需复核标记；旧内容留在审计历史 |
| `people.clear <ref>` | 清空当前画像，保留历史和来源 |
| `people.archive <ref> [画像版本]` | 不带版本先预览人物及关联账号；确认版本后归档，释放档案容量，保留历史和来源 |
| `people.lock <ref>` / `people.unlock <ref>` | 禁止/允许模型更新该画像；管理员仍可编辑，合并前需解锁 |
| `people.summarize <账号ID>` | 手动触发总结，仍遵守锁定、审核模式和来源限制 |
| `people.pending [候选UUID]` | 列出画像及账号关联候选；指定 UUID 查看完整候选和证据 |
| `people.approve <候选UUID>` / `people.reject <候选UUID>` | 接受或拒绝；身份或版本已经改变时不能直接接受 |
| `people.history [修改UUID]` | 每页 10 次修改，支持 `--page`、`--account`、`--person`、`--action`；指定 UUID 查看完整前后差异 |
| `people.revert <修改UUID>` | 条件回滚；相关对象有后续变更时拒绝覆盖，需人工修正 |
| `people.pause` / `people.resume` | 暂停/恢复当前场景的模型维护，暂停仍可查询和人工编辑 |
| `people.mode <off\|review\|auto>` | 当前场景关闭模型维护、人工审核或自动接受画像；账号关联候选始终需人工审核，切换不自动审批已有候选 |

确信度是管理员表达的身份信念，不是统计校准概率，也不能用作管理员权限、账号所有权或授权证明。`pause` 和 `off` 不停止账号识别、来源记录及既有画像读取；完全停用请在控制台禁用插件。

### 从群友名单到人工确认

如已安装 OneBot 名单插件，可先在当前群查询账号，再建立关联：

```text
onebot.contacts.members -n 20
people.create 许仙
people.bind 123456789 <上一步返回的人物UUID> 0.9
people.show 123456789
people.sources 123456789
people.summarize 123456789
people.pending
people.pending <候选UUID>
people.approve <候选UUID>
people.lock 123456789
```

名单插件提供平台联系人事实，人物记忆插件维护“认作谁”和“记得什么”。名单账号可以先人工绑定；有普通发言后才积累总结证据。好友名单仍使用 `onebot.contacts.friends` 的既有权限规则，本插件不会把名单整批发给模型或自动建画像。

### 认错之后

```text
people.pause
people.show <旧账号ID>
people.history --account <认错的账号ID> --page 1
people.split <认错的账号ID> 新称呼
people.sources <认错的账号ID>
people.edit <旧人物UUID> 核实后保留下来的完整画像
people.resume
```

原始消息和证据中的账号不会被改成人物昵称。旧画像被标为需复核后，默认模型上下文和模型读取会暂时隐藏其正文；管理员仍能查看旧内容。画像复核或重新总结可以恢复正文，但“身份关联曾改变”提示会保留，提醒模型核对可能混同的旧 L2/L3 记忆。重新总结只采用当前关联账号的证据，不自动改写核心 L2/L3 历史或删除当时产生的记忆。

翻查较早的记录可用 `people.history --account <账号ID> --page 2`；`--person <人物UUID>` 按人物查，`--action bind` 等筛选操作类型。账号筛选会追溯其旧关联人物；`--account` 和 `--person` 二选一。

不再活跃的档案可以先执行 `people.archive <人物UUID>` 预览，再用 `people.archive <人物UUID> <预览中的画像版本>` 确认。归档移除当前人物、关联账号及相关候选；来源和审计保留，条件允许时可通过 `people.revert` 恢复。该账号之后再次发言会建立新的临时档案，继续保留身份关联改变的提示。

## 模型如何使用

当前说话者和 L1 最近活跃账号最多 6 人自动进入上下文，总计不超过 6000 字符。每个人最多注入 600 字画像；完整资料可通过 `person_memory` 查询。包含临时档案标记、UUID、账号关联确信度、锁定、需复核、身份关联曾改变的提示及待审核候选。平台消息 sender 保持原样。

上下文优先保留人物和账号的关联字段，画像按剩余空间缩短；可用 `person_memory read` 查询完整画像。

`person_memory` 提供五种操作：

- `read`：传入 `account_id`，读取当前场景画像、账号关联和版本。
- `search`：传入 `query`，按称呼/画像关键词返回最多 5 个简短结果，不依赖向量检索。
- `history`：传入 `account_id`（账号 ID 或人物 UUID），读取最近 10 次相关修改的元数据及有限变更摘要，不返回原始证据正文；完整差异由管理员用 `people.history` 查看。
- `propose`：传入 `account_id`、完整 `profile`、1–10 个 `message_ids`，以及从上下文或 `read` 取得的 `person_id`、`person_revision`、`account_revision`。来源必须是本插件实际记录的当前场景、当前账号消息；过期版本拒绝写入。
- `propose_link`：提交账号关联建议，包含上述来源及版本字段，以及目标人物 `target_person_id`、`target_revision`、`confidence` 和不超过 500 字的 `reason`。目标人物必须属于当前场景，候选始终等待管理员确认。

模型不能直接改账号关联、合并、拆分、审批、锁定或跨场景读取。画像默认提交待审核候选；`auto` 模式满足来源、版本和锁定检查后接受画像，账号关联候选仍需人工审核。来源检查证明消息来自哪里，不证明摘要理解正确，管理员可随时干预。

后台按账号累计消息、批次总结，全局最多一个模型请求，同一账号有冷却期，默认最多 32 个待处理任务。失败不会中断回复；`people.status` 可查看当前进程内最近结果/错误。重启后队列与冷却重新开始，已有档案、候选和审计仍在数据库中。

## 数据与边界

- 按平台、机器人账号、群频道或私聊对象隔离。同一账号在另一个群有独立档案；第一版没有跨群识别或跨群记忆入口。
- 每个场景保留最近 200 条来源快照，每条最多 1000 字符；候选引用的快照独立保存，不因近期缓存淘汰而丢失。摘要最多 2000 字，每个画像最多携带 20 条来源；更早的修改和来源可查审计记录。
- 每场景最多 50 个待审核候选（画像和账号关联合计）、2000 个账号及人物。达到档案上限可用 `people.archive` 归档不再活跃的人物，释放容量。人物/关联/候选是带 revision 的场景 JSON 状态，审计差异和近期来源分表持久化；这版适合群聊规模，暂不提供大型全局人物库。
- 待审上限只限制新增待审核候选；`auto` 直接接受的画像不占用待审容量，仍须通过来源、版本、暂停和锁定检查，检查失败时不会写入。
- 人物更新与审计以同一条带 `format=1` 的审计 INSERT 原子提交，以场景和下一 revision 的唯一 ID 仲裁并发；冲突重新读取并校验，持续竞争时最多重试 16 次后报错，不会静默覆盖。条件回滚后的版本继续递增，阻止旧模型结果趁回滚重新生效。人物写入不使用共享数据库事务，失败或取消不会回滚其他频道和插件已经接受的普通写入。YIB 自己的后台保留期清理也以独立删除重试，避免清理失败撤销并发接受的记录；SQLite 共享连接仍有驱动边界，第三方插件自行打开事务时，其回滚可能影响同连接上的普通写入，本插件不能隔离第三方事务。
- 状态表是可重建缓存，缓存写入失败或倒退不会否定已接受的提交；读取会按 revision 重放后续提交并尝试修复缓存。新场景首条提交保留模式默认值；旧库首次新格式提交在同一条记录保存旧 revision 和完整状态基线，不改变原审计差异与撤销含义。旧 UUID 审计继续可查和条件回滚。升级前请保留完整备份，并停止旧版本人物插件写入；新格式启用后不能直接降级为只读状态表的旧实现，也不能单独删除/截断审计表。基线建立前仍需旧状态表，建立后缓存丢失可由完整提交日志恢复。
- 取消在最终 INSERT 派发前生效；已派发的写入等待数据库完成，成功即视为接受，卸载与迟到取消不会再回滚已提交内容。来源以场景和消息 ID 唯一 INSERT，重复消息不改写原证据；接受后的来源淘汰失败只会暂时多保留快照，下次采集再清理。
- 人工完整编辑没有新消息来源，审计明确记录管理员及旧证据。`clear` 是清空当前画像，不是删除历史；如有完整数据删除要求，需要同时处理本插件三个表及核心历史。
- 卸载停止后台任务并移除工具/注入，数据库内容保留。候选/画像内容会发往管理员配置的模型服务；开启后台模型组或 `auto` 前，应了解本群的记忆使用约定。

本插件不把身份确信度接到 Jev 回复概率或管理权限上。之后可按需要增加候选排序、其他检索后端或人工确认入口。
